# Binance 多标的实时行情异动监控

Python 3.11+ 的独立行情报警程序。按配置扫描多个 USDⓈ-M Futures 标的，每 60 秒检查 15m K 线，发现已发生的明显上涨或下跌。包含控制台与 Telegram 通知；没有下单、预测、收益统计、交易回测或 AI 分析。

**网络修复：已定位本机系统 DNS 异常，项目提供应用内 DNS over HTTPS 解析，保留 Binance HTTPS 域名和证书校验。实际验证结果见 [VALIDATION.md](VALIDATION.md)。** 每次启动仍通过 exchangeInfo 检查全部标的。Telegram 未提供凭证，未进行真实消息投递。

## Hermes 运行（推荐）

项目支持交由 Hermes 定时扫描和投递，无信号时静默，不调用大模型。
使用 `market-monitor-hermes --config /绝对路径/config.toml`；部署步骤见
[integrations/hermes/README.md](integrations/hermes/README.md)。策略、行情校验及 SQLite 去重继续保留。

不需要重启。检测阈值不开放给命令行改写，只能回测后再改。

## 安装与运行

```bash
cd /Users/zhaoqing/program/stock-monitor
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'

# 不依赖网络，不发送 Telegram：合成上涨、下跌、横盘、盘中位移、反转
mm demo

# 自动化测试
python -m pytest -q

# 第一步：验证真实接口、所有配置标的及指标，保存 CSV
mm verify

# 完成一次真实扫描；默认只在控制台报警
mm once

# 持续运行；Ctrl-C 退出
mm run
```

`mm` 与 `market-monitor` 是同一个命令（`mm` 已装到 `~/.local/bin`，任何目录都能用，配置文件位置固定）。

支持 `python -m market_monitor` 的同等命令。TA-Lib 的现代 Python wheel 通常自带 C 库；如果当前 Python／操作系统没有匹配 wheel，需要先按 [TA-Lib Python 安装说明](https://github.com/TA-Lib/ta-lib-python#installation) 安装底层 TA-Lib，再安装项目。无需 Binance API Key。本机系统 DNS 曾把 Binance 域名解析到异常地址，示例配置已开启 `dns_over_https = true`：通过 Google 的 HTTPS DNS 动态查询 A 记录，按 TTL 缓存并在连接失败时尝试其他返回地址；不写死 IP、不修改系统 DNS 或 hosts、不关闭 TLS 证书校验。首次 DNS／TLS 建连较慢时会重新采样服务器时间，仍要求采样耗时不超过 5 秒。

DoH 模式对 Binance 直接连接，不使用环境代理；如果需要 `HTTPS_PROXY`，将 `dns_over_https = false` 后设置标准代理环境变量。DoH 服务不可用时明确失败，不使用过期 DNS 记录。Telegram 保持原有 httpx 网络配置。

`verify` 成功后在 `data/verification/` 保存真实主周期和 1m K 线 CSV。任何标的无效、不可交易、行情陈旧或指标不可用都会明确失败，不会自动替换成测试网、现货或合成行情。`once` 只要有标的未成功检查就返回非零退出码。启动失败需处理原因后重新启动；运行中单个标的失败会跳过并在下次扫描重试。

## 检测规则

**所有默认阈值均为初始经验参数，未经最优性验证。** 它们描述已经发生的价格运动，不预测后续方向。

| 类型 | 默认条件 |
| --- | --- |
| 快速异动 | 当前主周期 K 线或最近 15 分钟位移 ≥ 1.5%，或最近 30 分钟 ≥ 2%；同时位移 ≥ 2 ATR、分钟路径 ER ≥ 0.65，并通过持续确认 |
| 持续单边 | 最近 2～4 根已完成 K 线至少两次同向收盘推进，最后一步仍同向；净位移 ≥ 2% 且 ≥ 2 ATR（**不再校验 ER**，见下节） |
| 小回撤容忍 | 持续单边窗口中的单次反向变化不超过 0.35 ATR，当前价格也未明显反向回撤 |
| 结束／重置 | 最近两根完成 K 线的净变化 < 0.5%，且 ER < 0.35 或收盘价区间 < 0.5%；连续两根不同的完成 K 线满足才重置 |

上涨、下跌使用对称规则。当前 K 线发生显著快速反转时优先使用当前方向。**快速信号**的 ER 是相关分钟价格路径的效率，默认要求 ≥ 0.65，以过滤来回震荡（这条仍然有效，因为 1 分钟路径点数多、ER 有真实分布）。ER = 净位移绝对值 / 逐步位移绝对值之和；TA-Lib 没有直接提供 ER，故仅此简单公式自行计算，不能用 KAMA 输出冒充 ER。

### 为什么停用持续单边的 er_min

持续单边用 2～4 根收盘价算 ER，而循环按 `(2, 3, 4)` 顺序取**第一个**满足的窗口。`count=2` 时只有 2 段路径，条件又要求"两次同向推进"且"最后一步为正"，两段必然都为正 → 分子等于分母 → **ER 恒等于 1.0**。实测 170 个历史候选（13 标的 × 50 小时）：`count=2` 命中占 53%（ER 全部恰为 1.000），其余窗口最低 0.794，**低于 0.70 的候选为 0 条**。也就是说该门槛一次都没有拦到东西；要用它挡任何事件，阈值需要提到 0.79 以上，要挡掉 10% 得提到 0.926。因此判定逻辑里的 ER 校验已删除，`er` 字段仅保留展示。配置项 `er_min` 保留只为兼容旧的 `config.local.toml`，不再参与判定（`mm list` 会标注"已停用"）。

### 待观察字段（只记录，不参与判定）

以下字段进入信号 payload 与通知文本，用来积累真实分布，**不作为门槛**——避免用拍脑袋的阈值降低覆盖率。取不到值一律输出 `null`、通知里显示"—"，绝不填 0 冒充分析结论。

| 字段 | 含义 | 口径 |
| --- | --- | --- |
| `window` | sustained 实际命中的窗口根数 2/3/4 | fast 信号为 0 |
| `session` | 美东会话：`RTH` / `pre` / `post` / `night` / `weekend` / `holiday` | 按 `America/New_York` 判定；周末与 NYSE 整日休市（感恩节、耶稣受难日、6/19、跨年等）各自单列，避免拿假日的稀薄成交量当基准 |
| `vol_ratio` | 最近 60 分钟（4 根）均量 ÷ **同会话**历史中位量 | 同会话样本 < 8 根时为 `null` |
| `taker_buy_ratio` | 最近 60 分钟主动买占比（0–1） | 来自 klines 字段 9/10，同场订单流，尺度无关 |
| `atr_expansion` | 当前 ATR ÷ 近 50 根 ATR 中位 | 与检测同口径取 `[-5]`；>1 表示波动率仍在扩张，<1 常见于脉冲末端 |
| `oi_change` | 名义持仓量近 1 小时变化% | `/futures/data/openInterestHist`，只在出现信号时拉取 |
| `funding_rate` | 资金费率% | `/fapi/v1/premiumIndex`，同上 |
| `breadth` / `breadth_total` | 同向信号的标的数 / 配置标的数 | 本轮已扫标的 + 上一轮快照；60 秒为一轮，未扫到的标的滞后最多一个周期 |
| `atr` | ATR 绝对值（价格单位） | 没有它，`atr_units` 无法反算成价格，事后不能复算阈值 |
| `closes` | 命中窗口实际用到的收盘价 | sustained 为 3–5 个值；fast 为基准价与当前价 |
| `vol_quote` | 命中窗口的成交额（USD） | 与 `vol_ratio` 互补：比值说明相对放量，绝对值说明规模 |
| `oi_value` | 名义持仓量绝对值（USD） | 与 `oi_change` 互补，判断合约体量 |
| `thresholds` | 当时生效的阈值快照 | 含 interval / scan_seconds 与全部 detection 阈值；配置改动后历史记录仍可解释、可复算 |

`breadth` 在同一轮里逐个累积：先扫到的标的只能看到上一轮的快照，从第二轮起才会完整。它描述"当前仍在报警的标的数"，不是"本轮价格同向的标的数"。

`oi_change` / `funding_rate` 拉取失败只记 warning，**不影响扫描与报警**——它们是观测数据，不是判定条件。资金费率为正表示多头付费（拥挤偏多）。

### 参数消融：每个门槛实际约束了多少事件

方法：不改判定代码，只把某个门槛的取值放到永远满足，用真实行情（13 标的 × 最近 5 天、1235 个扫描 tick）重放 `detect()`。基线下 sustained 触发 54 次、fast 触发 2 次。

| 关掉的门槛 | sustained 增加 | fast 增加 | 结论 |
| --- | --- | --- | --- |
| `sustained_atr` | +45 | — | 约束力最强 |
| `sustained_pct` | +23 | — | 与 ATR 门槛部分重叠，但两者都绑定，不能删 |
| `pullback_atr` | +6 | — | 有效，最弱的 sustained 门槛 |
| `fast_er_min` | — | +9 | **fast 上最强**，与 sustained 的 ER 完全相反，必须保留 |
| `fast_atr` | — | +7 | 有效 |
| `fast_15_pct` / `fast_30_pct` | — | +3 | 有效；ATR 门槛承担了大部分工作 |
| `quiet_er` | 平静判定 713 → 599 | — | 不是死参数：单独贡献 114 次"平静"判定 |
| `quiet_pct`（幅度项） | 713 → 4 | — | 主导项 |

`sensitivity` 已删除（定义上重复），`er_min` 已删除（170 个候选 0 拦截），`changes[45]` 已删除（与 30／60 高度相关）。其余门槛都有实测约束力，保留。

### fast 路径有多哑（实测）

13 标的、各约 5 天 15m 数据重放 `detect()`：

| `fast_er_min` | 快速信号 | 涉及标的 | 折算 |
|---|---|---|---|
| 0.65（当前） | 2 | 2 | 0.4 次/天 |
| 0.50 | 3 | 3 | 0.6 次/天 |
| 0.40 | 6 | 4 | 1.2 次/天 |

意思是：快速信号本来就是"盘中大幅插针"级别的事件，5 天 2 次属于正常稀疏，不是坏掉。放宽到 0.50 只多 1 次/5 天，收益不足以抵消误报风险，**保持 0.65 不改**。这条以前只是"未验证"，现在有样本支撑。

### 量能为什么要分会话、为什么不能当可信度

同一标的的成交量在不同时段不可比。实测（13 标的最近 5 天，成交额占比）：正式盘占 45–55%，盘前约为正式盘的 0.41–0.58 倍，夜盘约 0.23–0.26 倍。用跨会话的滚动基准会把时段切换读成"放量"：同一标的下盘前读数的中位数是 1.6–1.9 倍，正式盘只有 0.75–0.85 倍。改为同会话基准后中位偏差从约 2.2 倍缩到约 1.4 倍。

即便归一化，这个比值仍然噪声很大：窗口从 2 根拉到 8 根，NVDA 的变异系数只从 1.56 降到 1.15，AMD 从 2.55 降到 1.88。因此量能只作展示，**不用来给报警打可信度分数**。

代币成交量相对正股也很小（实测 24h 成交额占正股 20 日均额）：NVDA 1.91%、AMD 1.14%、AVGO 0.35%、MSFT 0.32%、INTC 3.53%、MU 5.20%、SOXL 52.62%。大盘股上是零头，不能代表全场参与度；SOXL/MU 这类高波动标的才接近同量级。所以"有没有人真金白银在建仓"改用同场的 `oi_change` + `taker_buy_ratio` + `funding_rate` 判断，它们测的是该合约自身的仓位与订单流，不依赖跨市场可比性。

需要正股真实成交额时，正解是 Polygon.io 之类的官方 aggregate 数据源（付费、含完整成交量），只在离线回测里用来做基准归一化。Alpaca 免费档只有 IEX 切片，成交量覆盖不全，不能拿来做 z-score。

ATR、ADX、+DI、−DI 均直接使用 TA-Lib。ATR 基准排除最近四根已完成 K 线以及当前未收盘 K 线，防止异常运动抬高自己的比较基准。ADX／DI 只作辅助信息，不阻挡早期提醒。持续单边取已完成 K 线，快速信号允许使用当前快照；检测函数没有网络、系统时钟或持久化副作用，不读取未来 K 线。

额外缓存 65 根 1m K 线，用于计算最近 15／30／60 分钟涨跌幅，基准取目标时刻之前最近的分钟收盘价，时间误差小于一分钟。**45 分钟窗口已删除**：它与 30／60 的 Spearman 相关分别是 0.93 和 0.90，属于重复记录，通知里也从未使用。修改主周期后，持续单边窗口随主周期改变，固定分钟涨跌幅窗口保持不变。

## 行情和异常处理

- 启动检查 `/fapi/v1/exchangeInfo` 中所有标的的 `TRADING` 状态，不假定任何股票挂钩合约存在。
- `/fapi/v1/klines` 首次取 200 根主周期历史 K 线及 65 根分钟线；以后从倒数第二根的开盘时间增量更新，按开盘时间去重，保留最新版本。
- 连续性、OHLC 合法性、有限数、周期对齐、历史长度都必须通过检查。缺口不插值、不前向填充；丢弃该缓存，下一扫描重新拉取历史。新上市历史不足的标的不报警。
- 每轮用 `/fapi/v1/time` 校准服务器时间并通过本地单调时钟推进，区分完成／形成中 K 线。必须包含服务器当前时间桶；边界尚未返回新 K 线时跳过该轮。
- 额外使用 `/fapi/v2/ticker/price` 的最近成交时间检查新鲜度，默认最大 180 秒；低流动性或休市标的可能被跳过。行情失败、数据滞后、指标未就绪均不更新报警状态，更不会用上次缓存补发。
- 超时、网络错误及 5xx 有两次指数退避重试。429／418 根据 `Retry-After` 设置整个客户端的暂停时间，停止该轮扫描，避免对剩余标的继续轰炸。正常情况下约 60 次行情请求／分钟，另加服务器时间请求，顺序执行。
- 扫描周期从每轮开始计时。网络耗时超过扫描周期时，实际间隔会拉长；60 秒是轮询目标，不是严格延迟承诺。瞬间冲高又回落可能在两次轮询之间被错过。

Binance 官方接口说明：[USDⓈ-M Futures Market Data](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)。

## 板块级合并

同一轮扫描里同方向报警达到 `merge_min_symbols`（默认 3）就合并成一条"板块级"消息，罗列成员、板块均值、量能/主动买占比与持仓变化。**数据库仍按标的逐条记录**，冷却、日限、episode 去重语义完全不变——合并只影响推送文本，不影响判定，也不改变 `alerts` 表的统计口径。合并后的行 `detail` 记为 `batched:N`。

- 阈值可配：`0` 或 `1` 关闭合并，退化成逐条推送
- 只在同一轮（60 秒）内合并；跨轮的同向信号不会拼到一起
- 上涨和下跌分别计数：2 涨 + 2 跌不会合并
- 一轮中途被 429 限流中止时，已经预留的告警仍会经 `finally` 送出，不会烂在 `reserved`

实测效果（11-06 23:00 CST 那一波）：原本 5 条独立消息压成 1 条，成员与各项指标都保留。

## 升级提醒（同一波行情继续扩大）

首报之后 episode 还是 active，原实现只静默保持，于是一波行情从 2 ATR 走到 7 ATR 也只提醒一次。现在补一条规则：**同一方向、episode 未结束**时，若"从这段位移起点算起"的累计位移比上次播报又扩大 `escalation_atr`（默认 1.5）倍 ATR，且距上次提醒超过 `escalation_seconds`（默认 1800 秒），补发一条 `kind=escalation` 的提醒。

- 基准固定：`origin_price` 取**被报那段位移的首个收盘价**，`origin_atr` 取报警时刻的 ATR。用当前 ATR 会让波动率扩张把倍数压低，升级时刻不可解释。
- 累计位移取 episode 内的**最大有利位移**，单调不降：回撤不降档，来回震荡不会被诱导重复报。
- 不受 `cooldown_seconds` 约束（30 分钟间隔已经够密），但受 `daily_limit` 约束；日限满时**不落库也不推进档位**，配额空出来还能补。
- episode 结束（连续 `reset_bars` 根平静 K 线）时四列一起清零，下一波重新从首报开始。
- 两个参数任一设 0 即关闭。

实测（13 标的、近 500 根 15m）：29 条首报产生 **5 条升级**（17%），单事件最多 2 条；消息形如 `位移 2.1→4.3×ATR`。同向多只同时升级时并入板块消息，标题为"板块级上涨/下跌升级"。

报告与通知：`mm list` 会显示这两个参数；`alerts` 表用 `kind='escalation'` 区分，`payload.escalation_from` 记录上一次播报的位移。

## 去重与通知语义

快速信号默认需要在相邻有效扫描中持续满足条件至少 60 秒（`fast_confirmation_seconds = 60`）。首次候选不通知，后续仍满足条件且累计达到 60 秒才预约通知；已完成 K 线的持续单边信号直接确认。候选消失、方向改变、行情请求失败或两次观察间隔超过**标称扫描周期的 3 倍**（默认 180 秒），会重置快速确认。

确认前不占用每日限额，也不把该轮标记为已通知。等待状态存入 SQLite，短时间重启仍可延续确认，长时间离线后重新确认。设置为 0 可关闭这一步。

> 为什么是 3 倍而不是 1.5 倍：cron 里 "every 1m" 实测每 ~120 秒才真正触发一轮（本地 `executions.db` 里 323 次运行，间隔全部是 119–120 秒）。按 1.5 倍（90 秒）判断，每一轮都会被当成"断档"，快速信号永远走不到确认——线上两天 0 条快速报警就是这个原因。改成 3 倍后，120 秒的正常节奏不会打断确认，真断档（>180 秒）仍然会重置。

这会过滤瞬时触线，但快速提醒通常比旧版多等待一轮扫描；将扫描间隔改为 180／300 秒时，实际确认延迟也相应增加。ER 过滤也可能漏掉路径较曲折的真实异动。阈值仍是初始经验参数，需要结合后续报警记录观察，不能视为已验证的最优参数。

告警表不会无限增长：每轮扫描开头会调用一次 `maybe_prune`，按 `retention_days`（默认 180 天）删除更早的记录，同一天只做一次（`meta.last_prune_day` 记录）。想更激进的收缩用 `mm prune N`，它会额外 VACUUM。

## 监控中断心跳

部分标的失败时进程退出码仍是 0，cron 不会报错——以前这种情况完全静默，只能自己敲 `mm` 才知道少扫了几只。现在连续 `health_alert_rounds`（默认 3）轮不完整就推一条：

```
⚠️ 监控不完整（连续 3 轮）

最近一轮：11/13 成功｜11-07 09:35
缺失：AMDUSDT、MSFTUSDT
影响：这些标的这一轮不判异动，异动可能漏报。
```

- 同一告警至少间隔 `health_alert_seconds`（默认 1800 秒），不会每轮刷屏
- 恢复后推一条"✅ 监控已恢复：13/13"，只推一次
- 整轮失败（退出码 1）仍走 cron 的错误通知，不重复计数
- 状态存在 `meta.health`，重启不丢；两个参数任一设 0 即关闭

SQLite 以“标的 + 方向”保存一轮异动状态。同一轮只预约一次主通知，快速信号升级为持续单边仅更新状态。短暂低于触发阈值不会结束这一轮；必须等待上述震荡重置条件。两次重置观察必须来自连续的不同完成 K 线，重复扫描同一根 K 线不会累计次数，行情断档也不会当成震荡。

默认同方向冷却 3600 秒、首报每日最多 60 条，按 `Asia/Shanghai` 的自然日统计；升级提醒单独计额（`escalation_daily_limit = 20`），不占首报额度。

> 为什么从 30 改到 60：把 11-06 那波半导体抛压按当前规则整日重放，正好 30 条 = 原日限，零余量。而顶满之后 `status=suppressed`、episode 仍 active，当天不再重试——等于行情最猛的时候反而静音。升到 60 后正常日约 35 条（含升级），极端日仍有余量。被冷却或每日上限抑制的一轮会记录为 `suppressed` 并标记活跃，之后不把旧信号延迟补发。反向异动拥有独立状态，可以单独提醒。保留 SQLite 数据库才能在重启后继续去重；不要把多个进程指向不同数据库来监控同一组标的。

预约和状态更新使用 `BEGIN IMMEDIATE` 原子事务；**先持久化预约，再发通知**。Telegram 没有这里可使用的幂等发送键，因此采用至多一次发送尝试：网络超时或程序在预约后崩溃时不自动重发，以防重复。代价是可能漏达一次通知，不能保证“恰好送达一次”。控制台会先打印；SQLite 的 `reserved` 表示预约后未完成确认，`failed` 表示失败或结果不确定，`sent` 表示 Telegram 接口确认成功，`console` 表示仅控制台输出。失败尝试也占每日限额。数据库不会保存 Bot Token。

查看通知记录：

```bash
sqlite3 data/monitor.sqlite3 \
  'SELECT id,symbol,direction,kind,day,status,detail FROM alerts ORDER BY id DESC LIMIT 30;'
```

## Telegram

先创建自己的 Bot 并确保目标聊天允许 Bot 发送消息。在 `config.toml` 中设置 `[telegram] enabled = true`，凭证用环境变量提供：

```bash
export TELEGRAM_BOT_TOKEN='你的 Bot Token'
export TELEGRAM_CHAT_ID='你的 Chat ID'
market-monitor run
```

通知包含中文方向与类型、当前价格、15／30／45／60 分钟涨跌幅、ER、ATR 标准化位移、辅助 ADX、检测时间及 Binance 页面链接，并明确是已完成 K 线确认还是当前形成中的提前信号。HTTP 错误不会把含 Token 的 Telegram URL 写到日志。`demo` 永远不发送 Telegram。

## 配置与目录

`config.toml` 集中管理 symbols、interval、scan_seconds（如 60／180／300）、directions、cooldown_seconds、daily_limit、reset_bars、时区、新鲜度与指标阈值。**没有全局灵敏度系数**：所有阈值都是绝对值，逐项调参（旧的 `sensitivity` 只是把 5 个阈值乘同一个常数，与分别调参在数学上重复，已删除；旧覆盖里若仍有 `sensitivity` / `er_min` 会被忽略而不是报错，避免 cron 静默停摆）。周期支持 `1m/3m/5m/15m/30m/1h`。数据库路径相对于运行命令所在目录。

```text
src/market_monitor/
  config.py       TOML 配置和校验
  market.py       REST、限流、服务器时间、行情缓存与校验
  network.py      可选 DoH 动态解析、TTL 缓存和 TLS 域名保留
  detection.py    纯检测逻辑与 TA-Lib 指标
  state.py        SQLite 状态、限额、冷却和原子预约
  notify.py       中文消息与 Telegram
  app.py          verify / once / run 命令和扫描编排
  demo.py         可重复的合成行情演示
 tests/           算法、采集异常、状态、通知与管线测试
```

测试覆盖连续上涨／下跌、小回撤、普通震荡、小幅单边、极端波动、盘中快速异动、反转、缺口、NaN、过期／未来时间、指标预热、增量拉取、重复 K 线、429／418、网络异常、去重、升级、冷却、每日上限、重启、跨连接预约和 Telegram 模拟响应。这些是功能验证，不能代替真实行情上对覆盖率和通知密度的长期观察。
